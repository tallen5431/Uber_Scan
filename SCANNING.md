# Camera scanning — experiment

Point a second phone's camera at the driving phone, read the offer card, show
the rate. This is an experimental branch; the typed calculator on
`index.html` is the version to rely on.

Open it with the **📷 Camera** button in the main app's bottom bar, or go
straight to `/scan.html`. It works offline —
the OCR engine and its language model are vendored in `vendor/`, so nothing is
uploaded and nothing needs a signal. Camera frames are read and discarded; no
image is stored or transmitted.

## It needs HTTPS

Browsers only hand out a camera in a *secure context*: HTTPS, or `localhost`.
Over plain http on a LAN address — `http://192.168.1.20:8080/scan.html` — there
is no camera to open at all, and the page says so rather than failing quietly.
The **📷 Photo** button still works there, on the same reader.

To serve HTTPS, point the server at a certificate:

```sh
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout key.pem -out cert.pem -subj "/CN=$(hostname -I | awk '{print $1}')"

SSL_CERT=cert.pem SSL_KEY=key.pem PORT=8443 npm start
```

A self-signed certificate makes the browser warn once; accepting it gives a
real secure context and the camera works. Tailscale or a reverse proxy with a
proper certificate avoids the warning.

## Does it work?

Yes, on a simulated camera capture of a real offer card. Test frames are
generated by rendering a replica of the card and then degrading it the way a
lens does: 13° off-axis, perspective, 1.1px defocus blur, a diagonal glare
gradient and reduced contrast.

| Frame | Read time | Result |
|---|---|---|
| Clean screenshot | ~435ms | correct |
| Camera sim, whole phone screen | ~233ms | correct |
| Camera sim, cropped to card | ~207ms | correct |
| Camera sim, half resolution | ~133ms | correct |

End to end in the browser, including canvas preprocessing and rendering:
**~500–630ms per read**, on top of a one-time ~460ms engine start.

## Is it fast enough?

Comfortably. Two agreeing reads are required before a verdict is trusted, so
call it **1–3 seconds** to a confirmed answer on phone-class hardware — against
an offer window measured in tens of seconds. Speed was never the risk here.

## The real risk is the decimal point

Pay and minutes survived every single test configuration. The distance did not:
"3.6 mi" was read as "36 mi" in 8 of 10 preprocessing variants, and no amount
of upscaling, greyscale or contrast stretching fixed it reliably. A decimal
point is one or two pixels through a lens, and it is the first thing to go.

That single character inverts the answer. At $0.30/mi, a phantom 32 extra miles
turns a $7.09 offer into **negative** earnings, reported with total confidence.

So the parser cross-checks distance against time. Nothing averages highway
speed door to door once pickup, parking and shopping are in it, so a reading
above 55 mph is treated as misread:

- if the reading had no decimal point and shifting it one place lands somewhere
  plausible, the decimal is restored and the correction is **shown on screen** —
  never silently applied;
- otherwise the distance is marked unreadable and simply not turned into a
  mileage cost, because overstating the rate slightly is a far cheaper error
  than understating it enormously.

This guard fires on the real pipeline, not just in tests: the end-to-end run
reports `decimalRecovered=true` on the sample card.

## Shopping time

Shop & Deliver offers quote a time that assumes shopping is instantaneous. The
card in the sample says 34 minutes for 6 items at a Dollar General. Set
**seconds per item** in Targets and that time is added:

| | $/hr |
|---|---|
| As quoted | $12.51 |
| Less $0.30/mi for 3.6 mi | $10.61 |
| Plus 90s per item (9 min) | $8.39 |

## Testing without a rig

Hit **📷 Photo** and pick a screenshot. It runs the identical pipeline —
decode, crop, upscale, OCR, parse, render — so you can check the parser against
real offers before mounting anything.

## Running the tests

```sh
node tests/parser.test.js     # 60 checks, no browser needed
```

The browser tests live in the session scratchpad and need Playwright plus a
local server on port 8765.

## Known limits

- Tested against a rendered replica with synthetic lens degradation, **not**
  against a real camera pointed at a real phone. Glare from a windshield,
  autofocus hunting and rolling-shutter banding are all untested.
- Only Uber's current card wording is handled: `$X.XX`, `N min (D.D mi)`,
  `N items`, plus the rideshare `away` / `trip` split. A layout change breaks
  parsing, which is why the manual keypad stays the primary path.
- The mount is the hard part. The camera phone must see the card square-on,
  in focus, without glare, while both phones are moving.
- `vendor/` is ~15MB in the repo so that any phone gets a core build it can
  run; a given phone downloads only the ~4MB variant it needs, once.

## On a Raspberry Pi

A fixed-mount Pi camera is a better version of this idea and removes the
alignment problem — see [rpi/README.md](rpi/README.md). The perspective warp a
fixed mount allows also fixes the decimal-point failure described above.
